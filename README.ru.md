# pingtun

Экспериментальный IPv4-туннель поверх ICMP, написанный с нуля на Go.
Шифрование и обмен ключами выполняет библиотека WireGuard; ICMP-транспорт,
очереди, проверка запросов и параллельные логические каналы — собственные.
Код Hans не используется.

Это версия для лабораторных испытаний. Есть исходный транспорт v1 и включаемый
отдельно адаптивный v2. Полный цикл WireGuard и IP-пакеты проверяются как в памяти,
так и через настоящий TUN в изолированной сети с NAT, потерями и перестановкой.
Автоматического переключения рабочей сети пока нет.

V2 отправляет короткие служебные запросы в простое, увеличивает окно при передаче
данных, ограничивает темп отправки и уменьшает окно при потерях. Перезапуск сервера
обнаруживается отдельно и запускает новый обмен ключами без перезапуска клиента.
Это экспериментальная схема, которую ещё нужно проверять длительно и на разных
сетевых устройствах. По умолчанию сохраняется v1.

Команды `probe` и `probe-server` измеряют ICMP без TUN и WireGuard. Они проверяют
подлинность изменённого ответа и содержимое, поэтому ответ ядра не принимается
за работающий туннель. Исследование канала и воспроизводимый стенд описаны в
[LAB.md](LAB.md). Протокол, границы и результаты — в
[PROTOCOL.md](PROTOCOL.md) и [VALIDATION.md](VALIDATION.md).

Процесс создаёт только свой TUN-интерфейс. Адреса, маршруты, NAT и firewall
настраиваются отдельно; существующие VPN не перенастраиваются.

Параллельные каналы дают несколько одновременно ожидающих ICMP-запросов внутри
одной шифрованной сессии. Это не независимые физические пути и не обещание
суммирования скорости при общем ограничении ICMP у провайдера.

Сборка, запуск, расход фонового трафика и особенности ответов ядра описаны в
[README.md](README.md). Генератор `pingtun init` создаёт пару конфигураций с правами
0600 и не печатает ключи. Конфигурации с секретами нельзя публиковать.
